## F-01 (High) — deploy.js не гарантирует, что развёртывается проверенный bytecode

**Класс:** tooling/deployment. **Статус:** воспроизведена локальным harness. **Полномочия:** не нужна атака;
типовая последовательность действий оператора.

**Где:** `chain/deploy/scripts/deploy.js:21` (`artifacts.readArtifact` берёт то, что лежит в `artifacts/`),
`:23` (`sourceFiles` — только `contracts/*.sol` верхнего уровня + config + lockfile), `:24` (`compiler` — литерал,
не прочитан из build-info; `sourceDirty` только записывается), `:34` (`runtimeHash` записывается, но ни с чем не сравнивается).

**Механизм.** Hardhat 3 при `hardhat run` делает incremental compile: изменённые файлы компилируются
отдельным job с меньшим набором исходников. Под viaIR bytecode ядра зависит от AST ID всего
compiler input (F-09). После правки и отката `ODPPassportLib.sol` исходники байт-в-байт совпадают
с проверенными, но в `artifacts/` остаётся другой bytecode ядра — и `deploy.js` развёртывает его.

**Шаги (logs/deploy-harness-*.json):**
1. Чистая сборка → развернуть: runtime ядра `0x4d915a93…901c` (= проверенный).
2. Добавить комментарий в `ODPPassportLib.sol` → развернуть: runtime `0x5fa62bb9…`.
3. `git checkout` файла (исходник снова `0f8bb89a…98bb`) → развернуть: runtime **опять `0x5fa62bb9…`**.
   Manifest шага 3: `sourceFiles` идентичны проверенным, `compiler` тот же литерал; отличие видно только
   в `runtimeHash`, который скрипт не сравнивает. Также деплой при `sourceDirty: true` проходит без отказа.

**Ожидалось:** отказ, если bytecode ≠ проверенному; **факт:** успешное развёртывание другого bytecode.

**Влияние.** Вердикт аудита относится к bytecode `0x4d91…`. Неизменяемый адрес получит другой код,
который никто не проверял и который Polygonscan может не верифицировать по «правильному» standard-json.
После deployment исправить нельзя — нужен новый реестр и новое поколение. От приложения не зависит.

**PoC:** `tests/zz-deploy-harness.js` (копия deploy.js: гейт заменён на `AUDIT_LOCAL`, добавлен `AUDIT_INTERRUPT_AT`).
```
AUDIT_LOCAL=1 ODP_DEPLOY_CHAIN_ID=31337 ODP_DEPLOY_MANIFEST=/tmp/m1.json npx hardhat run deploy/scripts/zz-deploy-harness.js
echo "// c" >> contracts/ODPPassportLib.sol   # затем повторить; затем git checkout файла и повторить
```

**Варианты исправления.** (a) Скрипт сам делает `hardhat clean && compile` в том же процессе/CI и
отказывается при `sourceDirty`; (b) лучше: развёртывать из **зафиксированного build-info** (standard-json input +
output), хеш которого утверждён аудитом, и проверять `keccak(creationBytecode)` против закреплённого
значения до broadcast; после — сравнивать runtime с ожидаемым (для спутников с подстановкой immutables).
(c) В manifest писать sha256 compiler input/build-info, версию и хеш soljson/solc.
**Рекомендация:** (b)+(c). Совместимо со всеми принятыми решениями, контракты не меняются.
**Regression test / критерий закрытия:** harness-сценарий «правка+откат» и «dirty tree» завершаются отказом
до первой транзакции; clean-сценарий записывает build-info hash, совпадающий с утверждённым.

## F-02 (Medium) — компрометация ключа: stop XOR revoke, разрушение истории после stop

**Класс:** архитектура + спецификация. **Статус:** воспроизведена (`F-01`, `F-02` в `ZIndependentAudit.test.js`).
**Предусловие:** злоумышленник получил ключ issuer/P-M кошелька (тот же адрес, что у владельца).

**Где:** `ObjectDigitalPassport.sol:358` (revoke требует неостановленный профиль);
`ODPStatementJournal.sol:77-83` (retract без проверки active), `ODPPassportProofRegistry.sol:48-53`,
`ODPPassportConcerns.sol:40-48` (`_registered`), `ODPRegistryRelations.sol:82,183` (detach/leave после stop),
`ODPStatementJournal.sol:48` (новые заявления/коррекции требуют active).

**Сценарий.**
1. Атакующий выпускает вводящие в заблуждение паспорта и/или отзывает свежие легитимные (≤72 ч).
2. Владелец выбирает: (а) отзывать поддельные паспорта по одному, пока атакующий продолжает выпуск;
   (б) `revokeCreator()` — выпуск остановлен, но **отзыв поддельных паспортов больше невозможен** (EC 131).
3. После stop атакующий тем же ключом может: `retractStatement` всех Active заявлений (включая годы
   экспертиз), `withdrawProof`, `withdrawConcern`, `detachAffiliation/leaveAffiliation`. Всё терминально —
   вернуть Active нельзя.
4. Владелец после stop не может опубликовать `IssuerCorrection`/объяснение в журнале (EC 131).

**SPEC.** §17: «Compromise … can mint misleading descriptions and revoke its recent passports within 72h.
It cannot edit immutable older records.» Формально записи неизменны, но **текущий статус** всей старой
истории (proof/statement/concern) атакующий меняет необратимо, в том числе после stop. §13 прямо
разрешает retract после stop — ради легитимной очистки, но не учитывает компрометацию.

**Влияние.** Необратимо после deployment (семантика в bytecode). Клиент может частично смягчить:
пометить изменения статуса с `changedAt >= revokedAt` профиля как «после остановки профиля», но
изменения, сделанные до того, как владелец заметил кражу, неотличимы.

**Варианты.** (1) Принять и честно описать в SPEC §17/§13 + обязать клиент показывать
«изменено после остановки профиля»; (2) разрешить `revokePassport` в пределах 72 ч и после stop
(тогда владелец сначала останавливает, затем отзывает; но и вор сохраняет это право 72 ч);
(3) запретить retract/withdraw после stop (теряется легитимная очистка — прежнее решение AR-05);
(4) отложенный stop/“freeze window”. Любой вариант 2–4 — изменение прав, требует отдельного решения.
**Рекомендация:** решение до фиксации bytecode; минимум — вариант 1. **Регрессия:** тест F-01/F-02
переписать под выбранную семантику; критерий — SPEC §17 перечисляет все права скомпрометированного ключа.

## F-03 (Medium) — повторная отправка журнала/экспертизы создаёт дубли

**Класс:** контракт (ABI) / приложение. **Статус:** воспроизведена (`F-05`).
**Где:** `ODPStatementJournal.sol:45-74`, `ODPPassportProofRegistry.sol:68-105` — нет operationId/nonce,
нет уникальности (author, kind, passport, payloadHash).

**Сценарий.** Клиент публикует IssuerCorrection, транспорт таймаутит, клиент повторяет — обе транзакции
успешны: два Active заявления одного автора об одном паспорте, «две независимые цепочки». Для mint
проект специально ввёл operationId; для журнала — ничего, и `ODP_07_APP_HANDOFF.md` §4 не требует
durable job для statements. SPEC §13 запрещает выбирать «последнее», значит клиент покажет два
равноправных заявления одного автора — ложная множественность/актуальность.

**Влияние.** После deployment ABI не меняется; дубликаты навсегда (снять можно только retract каждого).
**Варианты.** (a) `publishStatement(..., bytes32 operationId)` с тем же шаблоном digest/AlreadyCommitted, что mint;
(b) только клиент: durable job + чтение `getStatementsByAuthorPaged` и сверка payloadHash перед повтором
(гонка с pending tx остаётся). **Рекомендация:** (a) до фиксации bytecode, иначе (b) обязательно в HANDOFF.
**Регрессия:** повтор того же operationId → `AlreadyCommitted(id)`, без второй записи.

## F-04 (Medium) — криптографические форматы носителя фиксируются раньше выбора носителя

**Класс:** спецификация/продукт. **Статус:** подтверждено анализом.
**Где:** `ODPEditionUnits.sol:134-175` (`ODP-UNIT-LABEL-v1`, `ODP-UNIT-ACTIVATE-v1`, personal_sign, packed layout),
SPEC §20.5–20.7 (100-битный код, Crockford, HKDF context), `ODP_07_ACTION_PLAN.md` этап 4:
«Если формат носителя требует изменения криптографических обязательств, решение принимается до фиксации bytecode».
Формат QR/скретча не выбран (`review/qr-07` — эксперименты).

**Влияние.** Если компактная этикетка потребует, например, более короткого кода, другого payload подписи
или EIP-712 вместо personal_sign, существующий спутник это не поддержит — нужен новый спутник/namespace,
а ранние тиражи останутся в старом. Не exploit, а необратимая продуктовая развилка.
**Рекомендация:** закрыть решение о носителе (или явно зафиксировать, что текущие payload/код — окончательные)
до deployment. **Критерий:** подписанный пользователем выбор формата + векторы для печати.

## F-05 (Medium) — manifest deployment недостаточен для поколения и воспроизводимости

**Класс:** tooling/спецификация. **Статус:** подтверждено анализом + harness.
**Где:** `deploy.js:24` vs `schema/bundle-0.7/generation.schema.json` (требует `generationId`,
`build.buildInfoHash`, `registryRuntimeCodeHash`, роли спутников); SPEC §7, §15.

- Manifest не содержит generationId, ролей спутников, buildInfoHash; схема `odp-generation-v1` ≠ `odp-bundle-generation-0.7`.
  Конвертера manifest → `generation.json` нет. Приложение не сможет сформировать требуемый `.odpass` из выхода deploy.
- `sourceFiles` не включает `contracts/test/ODPTestWallet.sol`, хотя он входит в compiler input и
  через AST ID влияет на bytecode (F-09). Для верификации в explorer нужен точный standard-json (16 файлов).
- Прерывание (`AUDIT_INTERRUPT_AT`): manifest `interrupted`, последний контракт `pending` с предсказанным адресом;
  resume нет — повторный запуск создаёт новый полный набор, прежние контракты остаются «сиротами» в сети.
  Это безопасно для записи (ничего не связано), но требует процедуры: никогда не публиковать адреса
  из `interrupted` manifest.
- Проверка сети ограничена `ODP_DEPLOY_CHAIN_ID` (работает: chainId 137 на локальной сети → отказ).

**Рекомендация:** один генератор, который из утверждённого build-info и receipts строит и manifest, и
`generation.json`, с проверкой runtime (immutables подставлены). **Критерий:** harness генерирует
`generation.json`, валидный по схеме и принимаемый `bundle.mjs` как trustedGeneration.

## F-06 (Low) — URL хостинга замораживаются в состоянии, оставленном атакующим

**Статус:** воспроизведена (`F-03`). **Где:** `ODPHosting.sol:33`. SPEC §13 признаёт заморозку после stop,
но не случай компрометации: phishing-URL, выставленные вором, останутся «официальными» навсегда.
Целостность защищена хешами, поэтому Low. **Рекомендация:** клиент никогда не открывает hosting-URL
без проверки хеша и показывает «адрес задан до остановки профиля»; решение о праве очистки после stop — отдельно.

## F-07 (Low) — единственный слот author attestation занимает ключ, выбранный issuer

**Статус:** воспроизведена (`F-04`). **Где:** `ODPAuthorAttestation.sol:129-156` (issuer выбирает authorSigner,
слот one-shot; после withdrawal повторно не заполняется). NatSpec (`:13`) «A compromised minting wallet
cannot forge the second» вводит в заблуждение: подделать подпись настоящего автора нельзя, но
занять слот своим ключом можно у всех ещё не аттестованных паспортов. SPEC §13 требует известного
authorSigner — то есть риск признан. **Рекомендация:** исправить NatSpec/SECURITY; клиент считает
attestation значимой только для ключа, известного из независимого источника; для независимых авторов —
журнал (kind 2).

## F-08 (Low) — маска якорей в JS для прототипных имён типов

**Статус:** воспроизведена (`F-07`). **Где:** `chain/tools/passport.mjs:9,32` — `bits[a.type] ?? 0x80000000`
по обычному объекту. Схема допускает любой type (`minLength:1`). Для `constructor`, `toString`, `__proto__`
выражение даёт `NaN|…` → 0: custom-бит не ставится, в отличие от SPEC §9. Другой клиент (Swift) вычислит
маску с custom-битом → «Anchor mask mismatch» на корректном паспорте, или паспорт с неверной маской
будет выпущен. **Исправление:** `Object.hasOwn(bits,type)` или `Map`. **Регрессия:** тест F-07 должен дать `base|0x80000000`.

## F-09 (Info) — причина расхождения incremental/clean bytecode

**Статус:** воспроизведена (`logs/compile-context-experiment*.log`). Тот же compiler, настройки и исходник ядра:
- полный input (16 файлов) = без тестового кошелька → runtime `50309e…`;
- только замыкание ядра (4 файла) → `b59cb5…`, 12131 байт;
- замыкание + **посторонний** файл `AAA.sol` с 0/50/200/400/800 объявлениями → `16c3be…`, `50309e…`, `b59cb5…`, `f29bc3…`, `b59cb5…`.
Порядок источников не влияет (solc сортирует), содержимое комментариев не влияет. Меняется только диапазон
AST ID ядра, который зависит от прочих файлов. Вывод: viaIR-вывод зависит от нумерации AST (имена Yul-функций
содержат ID). Это не ошибка корректности, но идентичность bytecode = идентичность **всего** compiler input.
Прежнее описание «отличался creation bytecode» неполно: отличался и runtime.

## F-10 (Info) — compiler advisories для 0.8.20

Официальный `bugs_by_version.json`: 0.8.20 затронут 7 багами; 0.8.37 — ни одним.

| Баг | Условие | Применимость |
|---|---|---|
| SpillSlotCollisionAcrossMutualRecursion, UnsoundSpillInMutualRecursion | viaIR + взаимная рекурсия | Нет: Yul (ir и irOptimized) всех контрактов без циклов вызовов (`logs/yul-callgraph.json`) |
| MemoryByteArrayElementDeleteClearsWholeWord, MissingSideEffectsOnSelectorAccess | legacy (viaIR=false) | Нет: viaIR |
| VerbatimInvalidDeduplication | verbatim | Нет |
| FullInlinerNonExpressionSplitArgumentEvaluationOrder | пользовательская optimizer sequence | Нет: стандартная sequence |
| LostStorageArrayWriteOnSlotOverflow | массив на границе 2^256 storage | Практически недостижимо (keccak-слоты) |

Рекомендация — **не менять компилятор молча**; решить до фиксации bytecode, переходить ли на актуальный
(с полной повторной проверкой). Ограничение: regex-парсер Yul.

## F-11 (Low) — нет эталона для обязательных клиентских проверок

SPEC §13 требует сверки statement payload (subject, journal, author, kind, previousId) с on-chain envelope;
HANDOFF §1 требует пересчёта digest mint для восстановления. В `chain/tools` нет ни валидатора
statement-0.7, ни функции `mintDigest`. Разные клиенты реализуют это независимо — риск расхождений
(как F-08). **Рекомендация:** добавить эталонные функции и векторы (не меняет контракты).

## F-12 (Info) — самообъявленные учреждения

Воспроизведено (`F-06`): 7 свежих кошельков регистрируются как P и поднимают `activeConcernCount` до 7;
P не имеет квоты выпуска. SPEC §3/§17 и SECURITY это признают. Риск в публичном getter-счётчике:
клиент не должен показывать его как сигнал. Оставить как согласованный компромисс.

## Проверено и подтверждено (без находок)

- **Нет admin/upgrade/callback** в ядре: чтение кода, отсутствие CALL в mint (их тест), ни одной внешней записи из спутников в ядро.
- **operationId:** digest = keccak(abi.encode(домен, chainid, registry, sender, entrypoint, весь tuple)); namespace per sender;
  replay проверяется до `_activeProfile` и calendar — восстановление работает после stop/revoke/смены месяца; при revert
  ничего не резервируется; квота не тратится. Конкурентные pending с тем же ID → второй `AlreadyCommitted`.
  Присвоить чужой результат нельзя (ключ mapping — msg.sender). Новый ID + тот же документ = второй паспорт — осознанная граница.
- **editionCommitment:** Solidity = JS = независимый Python (4 KAT, включая count 2^20, ненулевой labelSigner) — `logs/independent-edition.log`.
- **HKDF/код/адрес/лист/root:** 5 единиц вектора совпали в Python с собственной Keccak/secp256k1.
- **Merkle/подписи:** усечённый/удлинённый/искажённый/перевёрнутый proof, чужой индекс, high-s — отклоняются (seeded, 10 размеров дерева).
  `v∈{0,1}` в EditionUnits принимается как 27/28 (в AuthorAttestation — нет): несогласованность без уязвимости.
