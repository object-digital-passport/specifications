**Дата:** 15–16 сентября 2026. **Объект:** проект, ещё не реализация нового реестра.
**База:** `audit/odp-07-review-and-redesign`, `5d1db8fdd1c7bef013cdd98875671b9c9e9e4760`.
**База предыдущего аудита:** `d9e656ee5039d97d66fc7fe6df601fc9c7534960`.

> **Граница этого отчёта:** ниже зафиксирована проверка исходного проекта на `5d1db8f`. После неё пользователь поручил реализацию. Ссылки на строки и поведение старого кода относятся к `review/astra/baseline-contracts/` и `BASELINE_SPEC_5d1db8f.md`; 165 тестов ниже не являются прогоном новой версии.

## Вердикт

**Конструкция выдерживает при условиях. Документ пока не готов к реализации как однозначное техническое задание.**

Уменьшение полномочий ядра соответствует выбранному продукту: регистрация факта выпуска, отсутствие владения, ограниченный отзыв, независимые спутники. Возвращать governance, multisig или timelock для этого не требуется. Но из этого не следуют ни корректность оставшихся механизмов, ни обещание безболезненной смены спутников.

До реализации необходимо закрыть пять условий:

1. **Разорвать цикл подготовки тиража:** будущий `passportId` участвует в выводе ключей, корень которых уже должен входить в документ до присвоения этого ID. Обычный клиент сейчас не может выполнить такой процесс последовательно.
2. **Определить сохранение истории между версиями спутников.** Новая версия активаций получает пустое хранилище; без явного выбора адреса/истории ранее использованный код снова выглядит неактивированным.
3. **Задать единую канонизацию и подготовку документа.** Одного переноса `passportId:null` недостаточно: правила чисел/порядка ключей противоречат заявленному ECMAScript-поведению, а эталонный документ содержит несогласованные даты.
4. **Уточнить оставшиеся интерфейсы и полномочия:** агент выпуска против агента хостинга; судьба affiliation; остановленные профили во всех спутниках; отсутствие/снятие/история замечаний; источник времени и полнота чтения.
5. **Согласовать SPEC, ABI, схемы и тесты с новым контрактом**, включая предел 100-битного кода, статус на момент выпуска, 72 часа, отмену unit-passport и новый смысл версий. После написания кода нужны его собственные негативные и stateful-тесты.

Старый аудит полезен как набор наблюдений, но **формула «36 находок, четыре критические, удалением закрыты 16» не является надёжной оценкой риска**. Среди ошибок — неверное исправление ODP-02, чрезмерный вывод ODP-04, неподтверждённая предпосылка запуска ODP-01, неверное описание наблюдаемости private storage, и представление предусмотренных SPEC компромиссов как неизвестных пользователю дефектов.

Критическое последствие при уже захваченном администраторе не следует выдавать за открытую атаку любого пользователя.

### Ошибки старого заключения, влияющие на решения

1. **Отзыв не уничтожает историю.** Сохраняются карточка, хеши, время, creator и события. Меняется статус, часть операций закрывается и tier исчезает. Формулировки release decisions §4 о потере всей проверяемости завышают последствия.
2. **Один занятый concern-slot не блокирует `submitProof`.** Release decisions §5 смешивает два спутника. При этом блокировка второго замечания реальна и исправления заслуживает.
3. **Отмена владения не выводится из найденных багов логически.** Owner решал делегирование операций держателю; изменить эти права можно было отдельно. Здесь отмена принята как самостоятельное продуктовое решение — не как единственный способ устранить уязвимость.
4. **«Без нового поколения» до первого deploy — неверная цена решения.** Можно изменить ещё не развёрнутое ядро 0.7. Старый документ рекомендует отложить core-правки до 0.8, будто цена нового адреса уже понесена.
5. **Количество PoC не равно количеству проверенных находок.** Есть несколько PoC на одну находку и пункты только с чтением кода. «Каждый из 36 доказан своим тестом» неверно.
6. **Регрессионный набор должен проходить после исправления.** Старые exploit-тесты сначала выявляют изменение поведения; затем их заменяют assertions на отказ/корректный результат. Все PoC не обязаны падать после redesign: например, G2 про допустимые дубликаты должен продолжать проходить.
7. Release decisions сам противоречив: «первые пять блокируют», но сводка не блокирует решение 1 и блокирует 6/8. Это исторический материал, а не действующий список release gates.

## 4. Владение, классификация и роль удалений

### Где owner действительно был несущим

| Старое место | Реальная функция owner | После удаления |
|---|---|---|
| `transferPassport` | Единственный caller, меняющий держателя записи | On-chain передачи/получателя нет; клиент не должен обещать коллекционеру получение записи во владение |
| `updatePassportUrls` | Наряду с creator мог поддерживать доступность bundle | Hosting-спутник оставляет issuer/agent; держатель хранит bundle/зеркало, но не получает права менять официальный hint |
| `recordPassportEvent` | Держатель мог добавлять собственные сведения | P/M экспертизы не дают держателю равнозначного права; это сознательное сокращение продукта |
| `ODPAuthorAttestation.attestAuthor` | Мог занять единственный слот | Удаление убирает конкретный owner-сценарий, но оставляет доверие к creator и выбранному signer |
| `mintUnitPassport` | Signed unitOwner получал запись; независимость payer/owner | Полностью убрано; activation не создаёт получателя или паспорт |
| `getPassportHeader` | Возвращал текущего owner | Меняется ABI tuple, требуется пересборка всех consumers, в том числе author/units interfaces |

`lifecycleStatus` не становится «ложным навсегда», если его смысл — **статус на момент регистрации**. Новая модель именно это допускает. Ложным становится UI, который показывает его как текущий статус. Переименовать описание поля и контекст показа; для исторических слоёв не применять «последняя запись побеждает» между заявлениями разных P/M автоматически.

`domain` в карточке по SPEC — **область деятельности/классификация**, например `contemporary_art`, а не DNS-домен. Новый `creatorId → domain` использует то же слово уже для хоста. В интерфейсах/документах нужен отдельный смысл, например `identityDomain`, чтобы не направлять fetch на классификационную строку.

### Что удалено зря — точнее, где удалена реальная полезная задача

Самый существенный потерянный механизм — **`recordPassportEvent(kind=8)` / edition notice**, а не transfer. Он позволял issuer после закрытия окна сказать о ключах/ошибке/отзыве партии, ничего не стирая. Новая конструкция сознательно выносит историю, но **экспертиза P/M не является заменой issuer notice**: иной актор, иной смысл, требуется его участие. Сейчас полной замены в проекте нет. Её можно описать вне ядра, не отменяя решений 2/18.

Другой полезный механизм — запрет отзыва тиража после первой активации. Он не был ошибкой; его замена на часы снимает зависимость core от units, но возвращает возможность отзыва уже активированного тиража до дедлайна. Это нужно показать пользователю как цену решения 6, а не скрыть словом «закрыли критическую находку».

Остальные удалённые механизмы:

- Router решал нормализацию расширений; сейчас её выполняет клиент/issuer tooling.
- Unit-passport решал отдельную идентификацию предмета и его держателя; activation покрывает только код единицы тиража. Это осознанная утрата, не эквивалентная замена.
- Governance-setters выбирали общую конфигурацию; теперь её выбирает клиентский manifest.
- Owner/transfer представляли держателя записи; замены нет по решению 1.
- URL в core решал обнаружение файла; hosting-спутник заменяет только после определения его API/ролей.
- Freeze прекращал приём записей на цепи; внешняя политика поколений меняет признание клиентами, не прекращает записи.

Ни один из этих выводов не требует вернуть привилегированный адрес в реестр.

## 5. Отзыв в течение 72 часов

Из snippet Redesign §4.3 следует точное правило: `now > mintedAt+259200` запрещает; **ровно в `+259200` отзыв ещё разрешён**. Это корректная включительная граница, а не off-by-one, пока она так описана. В JS-модели проверены дедлайн, следующая секунда, остановка профиля и отказ агенту.

- Timestamp паспорта не меняется, поэтому обычными операциями продлить окно **той же записи** нельзя. Перевыпуск создаёт другой ID и другое окно; это не продление старого.
- Задержать mint до проверки документа можно; это снижает потребность в исправлении, но не устраняет опечатки, выявленные после выпуска. «Только ради ошибки» контракт не проверяет: любой ненулевой reasonHash допустим.
- У агента нет отзыва даже для выполненного им mint: `p.creator` — principal. Это полезное разделение полномочий, его надо сделать явным.
- `revokeCreator` до воровского отзыва блокирует его; после — не восстанавливает. Держатель с потерянным, а не просто скопированным ключом вообще не сможет отправить остановку. Порядок транзакций, доступность RPC и мониторинг решают исход гонки; «72 часа» — возраст доступных для отзыва записей, **не гарантированное время на реагирование после кражи**.
- Вор может остановить профиль первым и тем самым запереть ошибочные паспорта даже внутри окна. После этого новое ядро не должно считать их более достоверными только потому, что отозвать их уже нельзя.
- Секундная погрешность и выбор включения важны только возле дедлайна, не дают продлить окно на дни. Утверждение brief о «нескольких секундах» не следует из Solidity. В просмотренном [Bor develop](https://raw.githubusercontent.com/0xPolygon/bor/develop/consensus/bor/bor.go) есть отдельные правила времени, включая future-time allowance 30 секунд; это не аудит конкретной конфигурации mainnet. UI должен опираться на блок/подтверждение, не обещать успех по локальному таймеру.
- На четвёртый день остаются две живые похожие записи, если issuer выпускает исправленную. Клиент не вправе выбирать новую как замену по одному сходству или времени. Нужен внешний контекст и явное отображение обоих фактов.

**Цена отказа от указателя:** один storage-pointer дешевле постоянного ручного сопоставления/индексации спорных записей. Но pointer не решает, какая запись истинна, и создаёт собственную семантику доверия. При принятом решении 4 поле не предлагается вернуть; следует честно признать, что сэкономленный storage перенёс большую работу на проверяющего. Structured supersession уже был сознательно запрещён SPEC §20.13 для тиражей: напечатанные ключи старого выпуска не становятся ключами нового.

## 6. Ядро без администратора и граница внешних вызовов

### Что следует из проекта, а что ещё нельзя доказать

В перечисленном новом API нет глобальных admin-путей, а в snippet `revokePassport` нет governance. Но тел нового mint, профилей и handshake ещё нет: доказать по проекту отсутствие скрытой ветки `msg.sender`, setter, initializer или external call **невозможно**. Конструктор «пустой» — требование к реализации, не проверенный факт нового bytecode.

Существуют **локальные права субъектов**: issuer отзывает собственную запись, principal подтверждает своего агента. Поэтому буквальное «никакой адрес не может ничего особенного» неверно. Верная гарантия — **нет адреса с глобальной властью над чужими профилями или конфигурацией ядра**.

### Полный разбор исходящих связей нынешнего core

| Связь | Где в текущем `ObjectDigitalPassport.sol` | После заявленных удалений |
|---|---|---|
| `relations.mintAgentForCreator` | `_resolveMintPrincipal`, строки 855–857 | Уходит, проверка локального storage handshake |
| `relations.getCreatorPublishingDelegation` | `_canUpdatePassportUrls`, 622–624 | Уходит с URL-путём |
| Public linked library: `buildCreatorId` | 447 | Остаётся, если library не встроить |
| Library validators physical/digital/mixed | 420, 589, 600, 611 | Обычные три остаются, unit-путь удаляется |
| Library URL resolver | 524 | Уходит |
| Library event validator | 694 | Уходит |
| Library UTC calendar | 874 | Остаётся |
| Library ID formatter | 969 | Остаётся |

Public library calls выполняются через `DELEGATECALL`, в том числе из объявленных pure-функций. R15 подтверждает внешний opcode реальным trace минта. Это соответствует [Solidity 0.8.20 Libraries](https://docs.soliditylang.org/en/v0.8.20/contracts.html#libraries). Если цель только «не вызывать спутники», библиотека допустима как часть доверенного core. Если цель «никаких внешних вызовов», текущая архитектура ей не удовлетворяет.

Обратное направление иное: `ODPEditionUnits` вызывает `lockEditionRevocation` и `mintUnitPassport` в core. Brief смешивает входящие привилегированные hooks с исходящими вызовами реестра. Удаляются **оба направления зависимости**, но это не «два исходящих вызова core к units».

`passportExists` — чтение storage реестра, возвращающее bool, **не callback**. Оно улучшает проверку существования, но не заменяет чтение creator/revoked/type, необходимое другим спутникам. Изменение ABI header/media после удаления owner/URLs всё равно требует переписать author/units interfaces. Нельзя объявлять весь ODP-11 устранённым одним bool.

### Если дефект найдут после запуска

Сам контракт продолжит принимать транзакции. Обновлённые клиенты могут запретить новые mint в него и пометить поколение проблемным; старые/offline/независимые клиенты могут продолжать. Исходные записи остаются читаемыми, **если сам дефект не ломает их storage/read-path** — вечную читаемость нельзя гарантировать независимо от типа ошибки.

Внешнее уведомление должно различать адрес, affected block range, причину, какие операции перестали признавать, как читать старые записи. Полное «перестать признавать адрес» может неоправданно обесценить незатронутую историю. GitHub/SPEC достаточны как канал выбранной политики; недостаточны как техническая остановка всей экосистемы.

## 7. Тиражи, энтропия, Merkle и ключи

### Перебор

В holder-derivation индекс **не входит** в хеш ключа; один candidate printedSeed для данного editionContext можно сравнить с набором всех N адресов. Поэтому multi-target выигрыш N действительно применим. При равномерных 100-битных кодах ожидаемый порядок работы до любого совпадения — `2^100/N` candidate derivations, каждая содержит SHA и вычисление адреса из secp256k1 key.

| N | Требуемые биты | Эффективная работа с кодом 100 бит | Запас относительно округлённого требования |
|---|---:|---:|---:|
| 5 000 | 93 | 2^87,712 ≈ 2,535×10²⁶ | 7 бит, ×128 |
| 100 000 | 97 | 2^83,390 ≈ 1,268×10²⁵ | 3 бита, ×8 |
| 1 048 576 | 100 | 2^80 | 0 |
| 2³²−1 | 112 | ≈2^68 | Требование нарушено на 12 бит |

Термин «порог на цель» неточен: требуется не менее 80 бит **работы до любой удачной цели**, поэтому каждому секрету дают дополнительные `ceil(log2 N)` бит. Checksum не добавляет секретной энтропии. Его случайное ложное принятие ≈2⁻²⁵; формулировка SPEC «reject ... probability 1 in 33 million» перепутала отклонение и принятие. Для конкретного класса опечаток универсальный равномерный bound автоматически не доказан.

Дубликаты секретов по birthday bound при 100 битах и N=100 000 имеют вероятность примерно N(N−1)/2¹⁰¹ ≈3,94×10⁻²¹; это малая, но не нулевая вероятность. Производственный инструмент может проверить уникальность списка до печати. Нулевой secp256k1 scalar также должен исключаться вместе со значениями ≥n, хотя событие пренебрежимо редко.

### Merkle

Поддельный proof для честно построенного фиксированного root не найден: 109 негативных мутаций отвергнуты, правильные proofs для нечётных и чётных деревьев приняты. Причины стойкости:

- Leaf хеширует 24 байта: uint32 index + address20; внутренний узел — 64 байта.
- Нельзя прямо переиспользовать node как leaf без нахождения подходящего прообраза/коллизии SHA-256.
- Индекс находится **в листе** и определяет left/right, поэтому перестановка позиции ломает два связывания сразу.
- Proof ограничен 32 siblings; unitIndex обязан быть меньше unitCount.

Это не формальное доказательство SHA-256 и не exhaustively проверенный простор. `_proves` не проверяет точную высоту по `unitCount` и правило odd duplication само по себе: они предполагаются при честном построении root. Issuer может открыть нестандартный tree/count, особенно поскольку `openEdition` не сверяет anchorsHash с самим root. Это **не взлом Merkle**; обязательна независимая проверка root/count/list/labelSigner относительно hash-bound anchor. R04 показывает, что контракт принимает произвольный root для неподходящего/отозванного паспорта.

### Что бесплатно и что зависит от данных

Офлайн membership не требует записи, но требует **доверенно закреплённого root** и списка/готового proof. SPEC §20.3 уже требует список внутри `.odpass`; Redesign §6 сокращает это до публикации на домене. Нельзя потерять обязательную bundle-копию: при умершем домене построить proof из одного root нельзя. Для N=5000 список адресов — 100 000 сырых байт, для N=100 000 — 2 000 000; список публичен, но его доставка не гарантирована бесплатно/навсегда.

`isActivated/getActivation` — view, запись не нужна. Результат означает состояние выбранного satellite на выбранном блоке; отсутствие сети или потеря исторического satellite не означает «не активирован». Офлайн-проверка по bundle без ранее доверенного chain anchor подтверждает только внутреннюю согласованность.

### Уничтожение мастер-ключа

Криптографически проверить, что никто не сохранил копию ранее известного секрета, нельзя в этой модели. Threshold storage, свидетели, HSM/аттестация оборудования дают ограниченные организационные гарантии, не доказательство отсутствия всех копий, в том числе у печатника. Цена настоящей перестройки доверия — другой процесс выдачи/генерации секретов; для выбранной модели разумнее сохранить честное ограничение §20.14. Реестр это не исправляет.

## 8. Замечания: счётчик, пагинация, стоимость и доверие

### Ключ пары и счётчик

`abi.encode(passportId, raisedBy)` однозначно кодирует границы двух строк. Это исключает **encoding ambiguity**, не математически все коллизии `keccak256`: для конечного 256-битного хеша абсолютное «невозможны» некорректно.

В нынешних satellites:

- Affiliation склеивает **два проверенных фиксированных profile ID** длиной 17, поэтому для доступных write-путей граница однозначна. Произвольные параметры read/cancel не создают второго допустимого write-ключа.
- Mint-agent key — string + address20; units key — string + uint32 (+ address20), то есть одна переменная часть и фиксированный suffix. Это само по себе не тот опасный случай, что две произвольные строки.
- Wallet anchor — address20 + bytes32; author EIP-712 хеширует строки раздельно. Коллизия из неоднозначной упаковки здесь не воспроизведена.

Без тел нового `raiseConcern/withdrawConcern` нельзя найти реализованную ошибку `_activeCount`. Для буквальной машины состояний инвариант:

`activeCount[p] = число существующих пар (p,raiser), у которых withdrawnAt == 0`.

Raise отсутствующего/снятого: +1; withdrawal действующего: −1; отказ: 0. Re-raise не добавляет повторный элемент в исторические списки. Остановка профиля не является withdrawal и не меняет эту сумму. На 100 000 шагах модели расхождения не найдено; это проверка **одной явной реализации правил в модели**, не сертификат будущего Solidity.

Конкретная последовательность `raise → revokeCreator → withdraw` заканчивается отказом withdraw и счётчиком 1. Это соответствует §2.6. Если UI считает только действующие **профили**, его число станет 0 — тогда он считает другую величину, не найден баг storage counter. Нужны раздельные определения: все неснятые заявления, заявления доверенных профилей, заявления действующих профилей. Отозванный профиль не может исправить прежнее заявление в этом satellite: это цена принятого правила, которую надо показывать рядом с историей.

### Пагинация

Рост всего append-only массива не создаёт порога, после которого **любая** страница перестаёт читаться. При прямом обращении к `arr[offset+i]` сложность O(page size), не O(total) и не O(offset). R09 показывает одинаковые **32 273 gas** для двух реально записанных строк при total=3 и при синтетической длине 1 000 000. Длина изменена `hardhat_setStorageAt` только в EDR; миллион выпусков не моделировался, этот тест изолирует зависимость от длины.

Проблемы возникают при большом `limit`, неограниченной длине возвращаемых элементов или необходимости собрать **все** страницы. Текущий core также делает `offset+limit` до обрезания; `offset=1, limit=uint256.max` вызывает panic 0x11 даже для трёх элементов. Это отказ caller от собственного запроса, не глобальный DoS. Безопасная формула: проверить offset; `n=min(limit,total-offset)`; задать документированный cap страницы.

Универсального количества элементов для отказа `eth_call` нет: оно зависит от gas cap RPC, лимита размера ответа, размера строк, байткода и page size. Число для **не написанного** concerns-контракта было бы выдумкой. Разумный acceptance-test: реальные максимальные ID/URL, page 1/100/max, offset у конца/за концом, limit 0/maxUint, чтение на фиксированном blockTag. Для списка **ID** 100 элементов — удобная исходная политика, но gas нового контракта нужно измерить после реализации.

Приложение не должно брать badge непосредственно из общего `_activeCount`: он включает неподтверждённые профили. Список доверенных профилей позволяет опрашивать `getConcern(passportId,profileId)` адресно, не перебирать весь Sybil-спам ради одного badge. Для полного независимого просмотра всё равно нужны индекс/страницы и метка полноты. Если выборка оборвалась, «0 найдено на прочитанных страницах» не равно «замечаний нет».

### Арифметика денег

При **заданных в документе**, а не текущих рыночных предпосылках:

`151340 × 30×10⁻⁹ POL × $0,25 = $0,00113505`.

Для 5000 — **$5,67525 ≈ $5,68**, при 80 gwei и $0,40 — **$24,2144**. Округление до $5,70/$24 разумно. Но 151 340 — газ **старого** single-slot concern без `reasonUrl`, двух массивов индексов и нового события; он не измеряет цену нового проекта. На новых storage writes цена неизбежно зависит от первого/повторного случая и URL, измерить точную стоимость сейчас нечего.

**Дешёвая массовая пометка не исчезает.** Цена одинакова для добросовестного учреждения и атакующего. Отмена profile-level записи делает число записей линейным, но не делает массовую пометку экономически невыгодной. Кроме того, отсутствие batch-функции не запрещает одной транзакции вызвать `raiseConcern` многократно из контракта, зарегистрированного как P/M, в пределах газа. Все 5000 в одну обычную транзакцию не обещаются; утверждение «одной транзакцией массово невозможно» всё равно слишком сильное.

### Неполная/устаревшая база профилей

Сам контракт защищает только форму сообщения, авторство кошелька, существование паспорта и разделение слотов. Он **не защищает от правдоподобного ложного учреждения**. При неполной базе честный новый P/M попадёт в неподтверждённые; при устаревшей базе скомпрометированный доверенный профиль может сохранить выделение. Ни число профилей, ни prefix, ни отсутствие предупреждений не заменяют проверку идентичности.

Нужны дата/источник проверки, registry-scoped key профиля, политика устаревания, независимая проверка официального домена, отображение stopped/compromise-сведений и возможность пользователю проверить источник. Одна выбранная база — реальная централизация **интерпретации приложения**, хотя не доступа к записи. Это допустимо, если не выдаётся за истину протокола. Неизвестное/недоступное объяснение показывается неизвестным, а не опровержением заявления.

## 9. Газ, курьер и «бесплатно»

Собственный R10 на неизменённых контрактах, двухлистном дереве, короткой карточке `Genuine work` и пустых URL, дал в полном прогоне:

| Операция | gasUsed |
|---|---:|
| P-регистрация | 154 807 |
| Повторный physical mint уже существующего B | 546 546 |
| Первое замечание старого concern | 151 340 |
| Первая activation тиража (включая lock callback) | 94 069 |
| Следующая activation того же тиража | 60 845 |
| Открыть тираж 5000 | 118 967 |
| Первая activation, 5000, proof из 13 siblings | 109 771 |
| Следующая activation, 5000 | 76 558 |

Первые два числа не совпадают с 171 878/642 752 исходного документа; это **не опровержение** старых измерений, поскольку их точная карточка, длины строк, состояния storage, proof и receipt не приложены. Activation 63 486 тоже нельзя считать постоянной: газ зависит от высоты Merkle tree, первого lock, calldata signature с нулевыми байтами. Между собственными прогонами были небольшие различия calldata-gas. Новое ядро без URL/owner/lock требует новых замеров; переносить старые числа в его смету нельзя.

[EIP-170](https://eips.ethereum.org/EIPS/eip-170) ограничивает runtime code, не creation bytecode, как местами пишет SPEC. Размер старого runtime проверен; размер будущего smaller core ещё не измерен.

### Три обещания о курьере

1. **«Не может соврать».** Не может изменить edition/index/recovered key сохранив валидную подпись и честный root. Может лгать HTTP-ответом, скрывать receipt, задерживать/не отправлять. У него **есть подпись**, иначе нечего ретранслировать; у него нет приватного ключа. Клиент подтверждает результат чтением цепи.
2. **«Не может заблокировать».** Не может запретить отправку другими на уровне ABI. Может отказать в собственном транспорте/оплате. Пользователь без токенов и альтернативного спонсора практически зависит от него; permissionless entrypoint не гарантирует доступность спонсора.
3. **«Без него работает всё главное».** Membership/чтение/reuse lookup не требуют курьера; но нужен bundle/list и доступ к правильной chain-state. Новая activation не бесплатна без кого-либо, кто оплатит газ.
4. **Дополнительный критерий — переносимость и отсутствие хранения секретов:** пользователь получает/сохраняет сформированную подпись+proof, может передать другому отправителю; курьеру не нужен printedSeed, и API не должен его запрашивать. Домен подписи защищает от переноса на другой chain/satellite/edition/index, а UI обязан фиксировать этот контекст.

R05 показывает: итоговые **unitAddress и единица** не зависят от sender, но timestamp зависит от момента включения. Фронтран валидной activation не отнимает право и не меняет signer; он меняет время первого появления и заставляет вторую транзакцию откатиться. Уже включённая откатившаяся транзакция расходует газ. Симуляция уменьшает этот риск, но не гарантирует защиту спонсора от гонки после симуляции. NatSpec/SPEC §20.9 обещание «даже наивного спонсора нельзя разорить» слишком сильное.

Обычный HTTP-relayer технически работает по текущему `activate`. Но SPEC §20.9 отдельно содержит **MUST: sponsorship rule must be a contract**, а redesign описывает обычную HTTP-оплату. Нужно согласовать нормативный текст с принятым продуктом: это не доказанная эквивалентность двум вариантам спонсорства.

Для `additionalMetadata` разрешены произвольные ключи, поэтому numeric-key канонизация — реальный допустимый вход, не искусственный запретный случай.

### Версионирование: что допустимо без смены core

Новый spectator satellite может читать старое ядро без его перевыпуска. **Это техническая возможность**, подтверждаемая архитектурой, а не следствие нынешней формулировки §14. Добавление нового proof-формата может быть таким изменением; новый creator prefix, изменение квоты/отзыва, новые обязательные поля core или удаление enum-значений — уже нет.

Минимально различать:

- core generation: неизменяемый адрес/байткод/ABI и его собственный packed version;
- passport document version: правило канонизации/семантика документа;
- satellite implementation/domain + его история storage;
- bundle version: упаковка.

`major*16+minor` работает только при каждой части <16. **Шестнадцатая minor-версия не представима**; её нельзя молча кодировать как следующий major. Если документ развивается до 1.16 при прежнем core 1.0, packed core byte может оставаться 16, но только если SPEC явно разделит версии и задаст совместимость. Нынешнее правило совпадения версий proof satellite и core во введении тоже требует пересмотра. Не следует менять core byte ради чисто документной версии.

## 11. Пропущенные риски и арифметика ядра

### Квоты и открытые роли

C/B лимиты не являются глобальной защитой от спама: один P или M минтит безлимитно, новые кошельки тоже обходят per-wallet ограничение. Это уже признанный в SPEC anti-spam sketch. После переработки сочетание «P/M безлимитны + только они ставят concerns/proofs» не даёт автоматического доверия или скидки добросовестным учреждениям. Оно увеличивает нагрузку на client curation/indexing. Решение 15 не отменяется; в продукте нельзя обещать стойкость к Sybil на основании квот.

### Два календаря

Точный скрипт в `review/astra/check-models.mjs` рассматривает все точки смены Gregorian month и fixed bucket в интервале `[2026-01-01,2036-01-01)`. Получено:

- несогласие 2,2061199% времени;
- максимальный непрерывный интервал 146 556 секунд = **1,69625 суток**;
- **16** Gregorian-месяцев с двумя fixed resets.

Это позволяет расходовать части нескольких квот в одном календарном месяце, но не расширяет 72h revoke: его проверка использует секунды напрямую. Gregorian ID остаётся согласован с mint month. Риск невысок при открытых P/M, но обещание «1000 за календарный месяц» неверно. Если лимиты оставлены без изменений, описать их настоящие окна; если важна именно календарность — это уже отдельная правка реализации, не скрытая часть redesign.

### Отказ генерации ID

При условной модели независимых равномерных кандидатов, N=10⁹ номеров и n уже занятых, вероятность отказа **одной транзакции после 25 попыток** — `(n/N)^25`. Это не вероятность первого collision и не криптографическая гарантия источника случайности.

| Заполнено за месяц | Вероятность отказа 25 попыток |
|---:|---:|
| 5 000 | 2,98×10⁻¹³³ |
| 100 000 | 10⁻¹⁰⁰ |
| 1 000 000 | 10⁻⁷⁵ |
| 10 000 000 | 10⁻⁵⁰ |
| 100 000 000 | 10⁻²⁵ |
| 500 000 000 | 2,98×10⁻⁸ |
| 900 000 000 | 7,18% |
| 990 000 000 | 77,78% |

При полном заполнении выпуск в этом месяце невозможен. Проверка занятости предотвращает перезапись, даже если validator/отправитель влияет на candidate. `gasleft/prevrandao/timestamp` не дают честной криптографической случайности: нельзя использовать ID для лотереи, секретности или безопасности. Для текущей задачи подбор красивого/предсказуемого ID не даёт владения чужой записью. Реальный throughput ограничен газом сети задолго до типичного исчерпания миллиардного пространства; сетевой максимум здесь не измерялся.

`_creatorPassports` растёт навсегда, но bounded getter не сканирует всё. Нельзя объявлять неизбежный отказ одной небольшой страницы на 100 тысячах записей. Растут стоимость полного обхода, объём индекса/истории и зависимость от RPC; см. R09 и §8. У proofs есть настоящий unbounded read, у affiliation текущий список ограничен 100 активными детьми и сокращается при detach — прежний аудит зря ставит все эти массивы в один ряд.

### Что ещё не покрывают старые тесты

- Atomic first activation против revocation около дедлайна: после удаления callback оба факта могут сосуществовать; UI не должен терять revoked-state при чтении activation.
- Согласованность всех getters на одном blockTag и полнота логов после reorg.
- Handshake после остановки principal/agent: агент сейчас может вообще не иметь профиля. Нельзя случайно запретить все unregistered agents общей проверкой `getCreator(agent)`.
- Отмена pending request отсутствует в новом API. Подтверждение должно ссылаться на текущий непросроченный/неотменённый запрос по явно заданным правилам; не получать права из старой незавершённой заявки неожиданно для principal.
- ABI ошибки: EC(131) уже означает остановку профиля, redesign использует также EC(132); concerns диапазон 133–140 не конфликтует по номерам, но таблицу ошибок нужно вести централизованно. В snippet сказано «пять проверок», фактически их шесть.
- После удаления событий полезен тест неизменности всей карточки/хешей и timestamp при любых допустимых операциях; состояние отзыва — единственное исключение, состоящее из **трёх** полей, не одного bool.

До реализации документу достаточно получить однозначные ответы AST-01/02/03/05/08/09/11/14; это не требует очередного администратора или отмены принятых 18 решений. До развёртывания уже написанной версии нужны:

1. E2E-тираж из реального pre-mint документа: код → root → mint → assigned ID → activation, без заранее выдуманного ID и без фиктивного anchorsHash.
2. Property-тесты 72h/issuer stop/agent scope, неизменности хешей, author key identity, concerns counters/re-raise/pagination.
3. Два поколения satellites и старые подписи/labels: клиент не теряет историю и корректно указывает источник.

5. Новые compiler/ABI/runtime hashes, газ на первом/повторном/максимальном input и реальная bounded-read нагрузка; затем отдельный независимый аудит реализации.
