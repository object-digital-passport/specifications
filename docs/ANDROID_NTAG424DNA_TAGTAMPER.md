# Android guide: NTAG 424 DNA TagTamper with ODP

This guide describes the practical `ODP + NTAG 424 DNA TagTamper` stack when the browser alone is not enough.

Short version:

- Use `ODP web` to mint the passport, publish `nfcPublicKey`, build `.odpass`, build `odpOffline`, and anchor `ndppCommitmentHash`.
- Use `NXP TagWriter` to write the tap carrier.
- For the current Pixel pilot, use the `ODP Android Companion` APK to import the Android handoff, run the live scan, attempt EV2/authenticated reads, and compare protected-file bytes against on-chain `nfcPublicKey`.
- Keep `Tag TrustLink Android` (or another compatible NTAG 424 DNA app) as a useful cross-check or fallback reference when you want an external second opinion on chip authentication or TagTamper state.

These are different trust steps:

1. opening a carrier is not chip authentication,
2. chip authentication is not yet chip-to-passport binding,
3. chip-to-passport binding comes from comparing the documented live mirror-profile result with on-chain `nfcPublicKey`,
4. ODP `.odpass` / `dataHash` verification is separate again.

ODP remains the registry and hash-verification layer. Android is the NFC runtime.

## What each tool does

### ODP web

Use the ODP web pages to:

- mint the passport
- store `sealType`, `nfcModel`, and `nfcPublicKey`
- build `.odpass`
- generate compact `odpOffline v0.1`
- export an NFC carrier file
- anchor an NDPP / offline payload fingerprint on-chain
- verify the registry record, issuer, and file hashes

Important: `ndppCommitmentHash` anchors the **raw offline / NDPP payload bytes only**. It does not hash the whole NFC carrier.

### NXP TagWriter

Use TagWriter when you want an NFC carrier that opens something useful on tap.

Typical use:

- write a standard URL / URI record that opens the ODP Verify page
- or write the exported ODP `.ndef` file generated by [`frontend/passport.html`](https://github.com/object-digital-passport/object-digital-passport.github.io/blob/main/frontend/passport.html) in the website repository

TagWriter writes the carrier / entry layer only. It does **not** authenticate the chip, does **not** read TagTamper state, and does **not** verify `.odpass` / `dataHash`.

### Tag TrustLink Android

Use Tag TrustLink for NTAG 424 DNA / TagTamper operations such as:

- chip-side validation
- secure URL / secure message flows
- TagTamper status reading
- validation against an NXP-side project or validation endpoint

Tag TrustLink is the chip-authentication step. It does **not** verify the full ODP passport by itself.

## Hardware and software

Minimum recommended setup:

- Android phone with NFC enabled
- real `NTAG424DNA_TAGTAMPER`
- ODP passport minted as `physical` or `mixed`
- `nfcModel = NTAG424DNA_TAGTAMPER`
- `nfcPublicKey` from the real chip written into the ODP passport

For a first practical prototype, Android is the best target. iPhone may be useful through a native app, but not through the browser alone.

## Pixel pilot protocol

Use this as the short practical test path for the current pilot with the **guided** Android companion:

1. Mint the passport in ODP web with `nfcModel = NTAG424DNA_TAGTAMPER`, record `physical.seal.nfc.uid` in `passport.json`, and publish the 16-byte EV2 application key as on-chain `nfcPublicKey`.
2. Export the Android handoff from `Verify` (after loading `passport.json` / `.odpass` so `nfcUid` is included) or `Manage passport`; the pilot preselects `odp-ntag424-ev2-symmetric-cr-v1` when `nfcPublicKey` is 16 bytes.
3. Install the Android companion debug APK on a Pixel with NFC enabled.
4. Open the handoff and follow the guided screens (`Get setup` → `Review values` → optional file → `Tap NFC now`).
5. Optionally import the local `.odpass` or `passport.json` on the optional-file step so canonical `dataHash` can also be checked on-device.
6. If the target tag requires EV2 auth, open `Operator tools`, enter local session auth inputs, then return to guided scan or scan from operator mode.
7. Tap the object with the Pixel. Read the plain-language result first, then `Technical details` if needed. For TagTamper passports, look for **`highAssuranceSeal = pass`**: EV2 key match + authenticated TagTamper INTACT + chip UID match when expected.
8. Use Tag TrustLink only as an additional reference if you want a second verifier path; it is no longer the primary pilot flow.

## Recommended issuer flow

### 1. Prepare the chip

Provision the physical tag on the phone or in NXP tooling.

**ODP Android Companion (recommended on Pixel):** Issue workflow → **Prepare to provision** → confirm → tap tag → copy `odp-chip-provision` JSON. Provision keeps NDEF **writable** (EV2 key 0) until the **Write NFC carrier** step after mint, which then locks CC/NDEF read-only.

**NXP TagWriter / PC:** same outcome if you already personalized the tag elsewhere.

You need at least:

- the real chip
- the **16-byte EV2 application key** from provisioning (this becomes on-chain `nfcPublicKey`)
- a successful **issuer-chip-setup** scan in Android companion **before** mint (see [ISSUER_NFC_FLOW.md](./ISSUER_NFC_FLOW.md))
- the tamper-aware physical installation on the object

Library: provisioning uses vendored code from [AndroidCrypto/Ntag424SdmFeature](https://github.com/AndroidCrypto/Ntag424SdmFeature) (`net.bplearning.ntag424`, MIT). See [odp-android-companion/ntag424-dna/NOTICE.md](https://github.com/object-digital-passport/odp-android-companion/blob/main/ntag424-dna/NOTICE.md).

### 2. Mint the ODP passport

In [`frontend/passport.html`](https://github.com/object-digital-passport/object-digital-passport.github.io/blob/main/frontend/passport.html) (website repository):

1. choose a `physical` or `mixed` object
2. choose NFC seal (`sealType = 1` or `3`)
3. set `NFC model = NTAG424DNA_TAGTAMPER`
4. paste the chip public key into the NFC section
5. finish minting as usual

This creates the public ODP record that later binds the chip result to the passport.

### 3. Build the offline / NDPP payload

In the passport manage modal:

1. open `Manage passport`
2. go to `Offline payload / NDPP`
3. generate the compact payload
4. optionally enable the NDPP-compatible carrier mode
5. download:
   - `CBOR` for the raw payload bytes
   - `NDEF file` for Android / NFC writing flows
6. if desired, anchor the payload fingerprint in the NDPP slot on-chain

If you use the NDPP-compatible carrier mode:

- the **first** NDEF record is the ODP Verify link
- the **second** record carries the deterministic `odp:off` payload
- `ndppCommitmentHash` still hashes only the raw payload bytes from that second record
- `ndppCommitmentUri` should point to a hosted copy of those same raw public payload bytes, not to the Verify page

The ODP web UI also shows an Android helper block with:

- Passport ID
- Verify link
- on-chain NFC model
- on-chain chip key

Use these values when switching to Android tools.

## TagWriter flow

Use this when the main goal is: "tap the object and open ODP verification."

Recommended pattern:

1. write the `odp://` URI as the first record — it names the passport and nothing else:

```text
odp://ODP-2026-03-004829301
```

2. if you want the ODP offline payload on the same carrier, write the exported `.ndef` file instead
3. add an HTTPS record only if you have decided to accept what it costs — see below

**Do not write a hostname unless you mean it permanently.** `SPEC.md` §12.2 is explicit that no
hostname is printed: a URL on a tag is a promise about a server, fixed onto an object that will
outlive it. This documentation used to recommend writing the project's GitHub Pages URL here.
That was wrong, and any tag written that way keeps pointing wherever that address ends up.

An HTTPS record is a real convenience — a phone with no ODP handler opens something instead of
nothing — so it stays available. It is a choice with a consequence, not a default.

Practical notes:

- URL-first is the most phone-friendly entry layer
- opening that URL is only the carrier-opening step
- it is not yet chip authentication and not yet a passport-integrity decision

## Tag TrustLink flow

Use this when the main goal is: "authenticate the NTAG 424 DNA TagTamper chip and read tamper state."

Recommended operator flow:

1. tap the object with Android
2. use Tag TrustLink to validate the chip-side response / secure-message flow
3. read the TagTamper state there
4. compare the documented live mirror-profile bytes from the Android result with on-chain `nfcPublicKey` in ODP
5. then use ODP Verify to compare:
   - Passport ID
   - issuer / creator
   - object details
   - `.odpass` / `dataHash`
   - optional image / offline payload hashes when relevant

That gives you separate answers to separate questions:

- "Did the chip authenticate?"
- "Was the seal tampered?"
- "Does this chip match the passport bound on-chain?"
- "Does the canonical passport data match the registry?"

## Verifier workflow

For a field verifier:

1. tap the object
2. if the tag opens the ODP Verify link, inspect the passport record
3. if higher assurance is needed, use Tag TrustLink on Android
4. confirm separately:
   - carrier opens the expected ODP verifier entry point
   - chip authenticates
   - tamper status is acceptable
   - chip public key matches on-chain `nfcPublicKey`
   - `.odpass` / `dataHash` / images match where needed
   - optional NDPP / offline payload matches `ndppCommitmentHash` when that layer is used

## What web can and cannot do

The browser can already:

- show the ODP registry record
- show `nfcModel` and `nfcPublicKey`
- generate `odpOffline`
- export NFC carrier files
- anchor NDPP / offline payload hashes
- verify `.odpass`, images, and public registry data

The browser does **not** currently do:

- low-level NTAG 424 DNA EV2/authenticated-read flow
- TagTamper state reading
- direct secure chip authentication

That is why the current practical architecture is:

- `web` for ODP registry and payload tooling
- `Android app` for chip authentication and tamper status

Low-level NTAG 424 DNA work may be informed by references such as `AndroidCrypto/Ntag424SdmFeature`, but that should stay a technical input, not the architecture of the ODP verifier itself.

## Recommended current pilot

If you want a realistic first deployment:

1. use ODP web for issuing
2. use a URL-first NFC carrier for tap entry
3. use the ODP Android Companion APK on a Pixel for handoff import, EV2/authenticated reads, and pilot `chipKeyMatch`
4. use ODP Verify for the registry and file-integrity side
5. compare the Android companion result with on-chain `nfcPublicKey`
6. use Tag TrustLink only as an optional cross-check, not as the main pilot path

That already gives you a workable ODP + TagTamper stack for the current pilot, without claiming a fully generic spec-max verifier or a fully specified native arbitrary challenge-response path.

For the dedicated-app scope, see `docs/ANDROID_VERIFIER_MVP.md`.
