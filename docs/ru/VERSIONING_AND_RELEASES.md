Этот документ объясняет, как **версии продукта** (например **v0.1**), **`main`** и **теги git** работают вместе — и что на практике значит «я больше не хочу менять v0.1».

## Что неизменяемо по устройству

| Механизм | Что он фиксирует |
|-----------|----------------|
| **Тег git** (например `v0.1`) | Указывает на **один коммит навсегда**, если только кто-нибудь не **удалит или принудительно не сдвинет** тег (после публикации так делать не надо). |
| **Задеплоенный смарт-контракт** | Байткод по данному адресу не меняется (если только не использовать обновляемый прокси — этот проект его не использует). |
| **GitHub Release**, привязанный к тегу | Человекочитаемые заметки и файлы для этого тега; текст редактируется, но код закрепляет именно связь **тег → коммит**. |

Итого: **«v0.1» как выпущенный снимок** = **коммит**, на который указывает тег **`v0.1`** (плюс приложенный GitHub Release, если он есть). Второй репозиторий не нужен; хватает одного репозитория и тегов.

## Для чего нужен `main`

- **`main`** — это **движущаяся линия разработки**. В ней могут лежать исправления и новая работа в сторону **v0.2** (или **v0.1.1** — см. ниже).
- Новые коммиты в **`main`** **не** меняют коммит, на который уже указывает **`v0.1`**, — если только не перетегировать или не удалить тег (после релиза не надо).

Типичный ход:

1. Вы заканчиваете работу над v0.1, ставите тег **`v0.1`**, публикуете GitHub Release, при необходимости деплоите страницы с этого коммита.
2. Дальнейшая разработка **следующей** линии протокола или инструментов идёт в **`main`** (например v0.2). Тег **v0.1** по-прежнему помечает старый снимок.

## «Хочу для v0.1 только исправления багов, а потом заморозить»

В терминах git это читается так:

1. **Заморозить линию** = перестать считать **`main`** «версией v0.1» и считать последним снимком v0.1 **тег `v0.1`**. Новая работа в **`main`** — это **v0.2-dev** (или отдельная ветка, см. ниже).
2. **Критические баги**, которые надо выпустить **без** полноценной v0.2:
   - Вариант **A** — **патч-тег** с ветки, отрезанной от **`v0.1`**: например, ветка `release/v0.1`, туда черри-пик или коммиты с исправлениями, затем тег **`v0.1.1`** и заметка «hotfix».
   - Вариант **B** — исправить в **`main`** и поставить тег **v0.2.0**, когда будет готово (пользователи v0.1 остаются на старом контракте и UI, пока не мигрируют, — зависит от вашей продуктовой истории).

Для багов **в контракте** обычно применим только вариант **A** либо **новый деплой** по новому адресу; фиксируйте письменно, какой адрес какому тегу соответствует.

## Один сопровождающий: можно ли «отнять у себя» право править v0.1?

- **Теги:** вы можете **решить не двигать** `v0.1`. Это выбор **политики**. Git не мешает владельцу репозитория удалить тег, если не задействованы **правила уровня организации** на GitHub или подобное.
- **Защита ветки** **`main`**: можно требовать **pull request** и запретить **прямые пуши**, в том числе **администраторам** (см. [`.github/BRANCH_PROTECTION.md`](../../.github/BRANCH_PROTECTION.md)). Тег **`v0.1`** это не удаляет, но замедляет случайные изменения в **`main`**.
- Настоящее «я не могу это переопределить» в роли единственного владельца на GitHub сделать **трудно**: аккаунт с правами **owner** обычно может снова поменять настройки. Некоторые команды ради строгости заводят **второй аккаунт**, **правила уровня организации** или **подписанные теги плюс политику**.

**Практический подход:** считать **`v0.1`** **неизменяемым после релиза** — не перетегировать, письменно указать «поддерживается до …», а новую работу вести под **v0.2** в **`main`** или **`develop`**.

## Сводка

| Цель | Действие |
|------|--------|
| Выпустить v0.1 | Тег **`v0.1`**, по желанию GitHub Release, зафиксировать коммит контракта и Pages. |
| Держать v0.1 стабильной | **Не** двигать и не удалять тег **`v0.1`**; хотфиксы → **`v0.1.1`** с ветки **release/v0.1**, если понадобится. |
| Новые возможности | **`main`** (или ветка **`v0.2`**) → позже тег **`v0.2.0`**. |
| Более строгий процесс | Защита ветки + PR (см. `.github/BRANCH_PROTECTION.md`). |
