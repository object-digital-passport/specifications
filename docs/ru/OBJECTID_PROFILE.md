# Профиль совместимости ODP с Object ID · черновик v0.5

*Перевод справочно. Нормативный оригинал — только на английском: [`docs/OBJECTID_PROFILE.md`](../OBJECTID_PROFILE.md). Этот текст может содержать ошибки; при расхождении верен английский.*

*Профиль опциональный. Нормативные правила ядра остаются в [`SPEC.md`](../../SPEC.md) ([перевод](SPEC.md)).*

> **Профиль описывает закрытую линию v0.5.** Он раскладывает категории Object ID в отдельный
> блок `objectId`, который существовал только в документе формы v0.5. В линии v0.7 этого блока
> нет: те же категории опознания стали полями и якорями самого `passport.json` — см.
> [`SPEC.md` §9](../../SPEC.md#9-passport-json) и
> [`schema/passport-0.7.schema.json`](../../schema/passport-0.7.schema.json). Текст ниже оставлен
> как есть — для той линии, которую он описывает.

## Зачем это

Профиль заставляет паспорт ODP одним документом обслуживать **две дополняющие друг друга задачи**:

1. **Подлинность** (ядро ODP): та ли вещь перед вами, что зарегистрирована? Ответ дают якоря в цепи — `dataHash`, `fileHash`, хэши изображений, проверка пломбы (SPEC §10–§11) — плюс институциональные подтверждения (`submitProof`).
2. **Документирование кражи и возврат** (Object ID): если объект потерян или украден, есть ли описание, достаточное для полиции, таможни, страховщиков и баз вроде реестра украденного искусства INTERPOL? Ответ дают данные по чеклисту Object ID, собранные ниже и криптографически заверенные временем при минте.

Задачи усиливают друг друга: те же *отличительные особенности*, по которым следователь опознаёт найденную картину, позволяют эксперту отличить оригинал от физической копии. Подделка может нести клонированную метку или скопированный QR — но она не понесёт заделанный трёхсантиметровый разрыв оригинала, надпись на подрамнике и точный рисунок кракелюра, а эти факты заякорены хэшем в цепи с меткой времени минта, предшествующей спору.

## Отношение к стандарту Object ID

[Object ID](https://icom.museum/en/resources/standards-guidelines/objectid/) — международный стандарт документирования культурных ценностей: **девять информационных категорий** плюс четыре шага (сфотографировать → определить категории → написать описание → надёжно хранить). Права принадлежат **ICOM** (Международный совет музеев).

> **О товарном знаке:** этот профиль *совместим с чеклистом Object ID*.
> Он **не** аффилирован с ICOM или J. Paul Getty Trust, не одобрен и не сертифицирован ими.
> Реализации НЕ ДОЛЖНЫ представлять паспорта ODP как официальные записи Object ID.

## Соответствие категорий

| Категория Object ID | Поле passport.json v0.5 | Требование профиля |
| --- | --- | --- |
| 1. Тип объекта | `domain`, `physical.category` | обязательно |
| 2. Материалы и техника | `physical.medium`, `physical.materials` | обязательно |
| 3. Размеры | `physical.dimensions` (и `physical.weight`, когда осмысленно) | обязательно |
| 4. Надписи и маркировки | `physical.marks` | обязательно, если есть на объекте |
| 5. Отличительные особенности | **`objectId.distinguishingFeatures`** (новое) | обязательно |
| 6. Название | `title` | обязательно (ядро) |
| 7. Сюжет | **`objectId.subject`** (новое) | обязательно |
| 8. Дата или период | `creationDate` (+ `objectYear`, если отличается от года минта) | обязательно |
| 9. Автор | `authorship.author` | обязательно (ядро) |
| Шаг 1: Фотография | `image` (+ `imageHash` в цепи) | **обязательно** для physical/mixed |
| Шаг 3: Описание | `description` | **обязательно** |
| Шаг 4: Надёжное хранение | сохранение `.odpass`; см. «Приватность» ниже | обязательная практика |

## Новые поля (блок `objectId`)

```json
"objectId": {
  "subject": "Зимний пейзаж: замёрзший канал, справа мельница, на переднем плане двое конькобежцев",
  "distinguishingFeatures": [
    "Заделанный разрыв 3 см в правом нижнем квадранте, виден при скользящем свете",
    "Синий мелом инвентарный номер 47-B на верхней планке подрамника"
  ]
}
```

- `subject` — что изображено или представлено. Свободный текст, одна строка.
- `distinguishingFeatures` — массив конкретных проверяемых наблюдений: повреждения, реставрации, производственные дефекты, неровности. Пишите каждый признак так, чтобы третья сторона могла сверить его с физическим объектом. Избегайте общих формулировок («хорошая сохранность») — они не идентифицируют ничего.

Оба поля входят в канонический документ и покрыты `dataHash`: после минта их нельзя отредактировать так, чтобы правка осталась незаметной (SPEC §10). Машинная проверка блока `objectId` жила в схеме v0.5, которой в репозитории больше нет; в линии v0.7 те же поля проверяет напрямую [`schema/passport-0.7.schema.json`](../../schema/passport-0.7.schema.json).

## Правила соответствия профилю

Паспорт соответствует профилю, когда:

1. Блок `objectId` присутствует и оба его поля непусты.
2. Для `objectType` `physical` или `mixed` присутствуют `image`, `description` и `creationDate`, а `imageHash` в цепи ненулевой (фотография в Object ID не опциональна).
3. Заполнены все применимые строки таблицы соответствия выше.
4. Эмитент сохраняет канонический бандл `.odpass` (шаг 4 Object ID).

## Приватность: модель «публикуем при происшествии» (важно)

Практика Object ID — держать документацию **конфиденциальной** до происшествия, а затем передавать её следствию. ODP поддерживает это изначально:

- Минтите с **пустым `dataUrl`**: в цепь уходят только хэши, а `.odpass` (фотографии, признаки, надписи) остаётся у владельца. Ничто о внешнем виде или местонахождении объекта не публично.
- После кражи владелец раскрывает `.odpass` — полиции, реестрам или публично через `updatePassportUrls`. После этого любой может сверить раскрытую документацию с **хэшами и меткой времени минта, попавшими в цепь до происшествия**: описание доказуемо не было написано задним числом.
- **Не кладите точные места хранения в изменяемое состояние в цепи.** `currentState.location` в публичной цепи читается кем угодно и навсегда. Пользуйтесь грубыми значениями («на хранении», «на выставке») или держите местонахождение вне цепи целиком.

## Сигнал «утрачен / украден» (дорожная карта, не в байткоде v0.5)

В эталонной линии v0.5 нет флага «утрачен/украден» в цепи. Временная практика и планируемое направление:

- **Временно:** владелец обновляет каналы вне цепи, а если задействована институция, профиль `P`/`M` может зафиксировать заявление через существующий спутник `ODPCounterfeitConcern`. Его семантика подходит не полностью (он утверждает «возможна подделка», а не «заявлено о краже») — используйте документ, заякоренный через `reasonHash`, чтобы изложить фактическое заявление.
- **Планируется (кандидат в v0.7):** отдельное состояние «заявлено об утрате/краже», поднимаемое владельцем (спутник или поле основного реестра), заметно показываемое верификаторами в момент сканирования, с проверяемой историей подъёма и снятия. Это превращает каждый верификатор в пассивную точку возврата: сканирование украденного объекта где угодно поднимает заявление.

## Указания верификаторам

Верификаторам, реализующим этот профиль, SHOULD:

- Отрисовывать девять категорий отдельным видом «карточка Object ID».
- Предлагать **экспорт на печать** этого вида для процессов полиции, страховых и таможни.
- Показывать `distinguishingFeatures` рядом с результатами по пломбе и хэшам во время физического осмотра — это человеческая экспертиза, дополняющая криптографические проверки.
- Показывать сигнал «утрачен/украден» (когда планируемый механизм выйдет) прежде любого результата о подлинности.
